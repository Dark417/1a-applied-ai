- **Most people use AI at 5–10% of what it can do**
  - There is a faster way — and it scales to enormous processes, not just personal tasks
  - It is the skill behind real roles at large companies: the difference between **doing one job** and **designing how a hundred of them get done**
  - The author learned it at a Danish university: a whole course on laying a process out as a diagram and making it as efficient as possible
- **What this covers**: what a graph is, the one test that makes your AI faster, the one pattern that pays, where graphs break, when a graph is the wrong tool, and how to build one in minutes
- **1 · Where this came from**
  - A month ago the field was all about **loops**; then Peter Steinberger (@steipete) posted: *"Are we still talking loops or did we shift to graphs yet?"*
  - A **loop** = one agent improving one thing on repeat: try, check, adjust, go again
  - The shift is not a better loop — it is a **graph of loops**: a network where cycles watch and correct each other, instead of one agent chasing one number alone
  - Engineers pushed back: it's a **decades-old idea with a new name**
    - True — and that's good news: a pattern that has run critical systems for 30 years is what you want to trust
- **2 · What a graph actually is**
  - A plan for your AI work, drawn out; it answers: **which jobs need to happen**, and **which job waits for which**
  - **Node (box)** = one job: one agent, one task, one input, one output
    - e.g. researching a competitor, writing a draft, checking a claim
  - **Edge (arrow)** = one job needs what another produced, so it waits
    - The arrow only counts when **something real passes along it**
  - **Nodes do the thinking. Edges carry the results.** That's the whole vocabulary
  - **Node contract**: one bounded job, a defined input, a defined output
    - Free-text output → only a human can read it
    - Fixed output shape → the next node can consume it without guessing
    ```text
    ▸ NODE CONTRACT
    JOB:     research one competitor's pricing (one job, nothing else)
    IN:      { competitor: "name", url: "https://..." }   ← passed in, never assumed
    OUT:     { price: number, plan: string, source: url, date: "YYYY-MM-DD" }
    SCHEMA:  enforced. if the agent returns free text, it's rejected and retried
    WHY:     a defined output is what lets the next node read this one
             without a human in the middle. that is what makes it wire-able.
    ```
- **3 · The test that finds the fake edges**
  - Walk your current workflow step by step and ask: **does this step actually need the result of the one before it?**
    - Yes → real edge, keep the order
    - No → no edge; the wait is wasted, the two jobs can run at the same time
  - Example: "review file A for bugs, then review file B"
    - The check on B never looks at A's result — they're sequential only because you typed them that way
    - Run side by side → finishes in the time of the **slower single file**, not the sum
  - You'll find **2–3 fake edges in almost any workflow** — each one is time thrown away
- **4 · Your current setup is already a graph**
  - "Do A, then B, then C, then D" is a graph — the saddest one: **a single straight chain**
  - It runs correctly, but **slowly and fragile**: no redundancy; if C stalls, D never happens and A's work is trapped
  - **First skill: redraw the chain**
    - For each arrow, ask the fake-edge question
    - Cut arrows that carry no data → the line collapses into **a few independent jobs running at once, feeding one job that needs them all**
  - Why it matters
    - Linear 40-step workflow: 40 points of sequential failure + latency of all 40 added
    - Same 40 jobs as a graph: only the real dependencies (usually **3–5**), finishing at the speed of the **slowest layer**
    - ≈ 5 minutes vs 15 seconds for the exact same work
  - **The model was never the bottleneck. The line you drew was.**
- **5 · The one pattern that pays: the diamond**
  - Any serious agent system: work splits → workers dig side by side → something checks → everything merges into one answer
  - Formal name: **fan out, reduce, synthesize**
    - **Fan out** to gather breadth
    - **Reduce** with plain code to compress
    - **Synthesize** with a final agent to write the answer
  - Claude's research feature runs exactly this: a lead plans angles, workers gather in parallel, findings get checked, one report comes back
  - Shift the question from "how do I make my agent do more steps" to **"where is the split, where is the merge"** — that one scales
  - When you say "workflow", Claude writes a script like this and runs the coordination as code → **passing results between agents costs zero extra context**
    ```javascript
    // a market-scan graph — the diamond, written by Claude when you say "workflow"

    const angles = [
      "pricing vs the top 3 competitors",
      "what buyers complain about in reviews",
      "the feature gaps in the category",
      "where the market moves in the next 12 months",
    ];

    // FAN OUT — one researcher per angle, all at the same time
    const raw = await parallel(
      angles.map(a => () => agent({
        task: `research: ${a}. every claim needs a source url + date.`,
        schema: Finding,        // validated output, not free text
        model: "cheap",         // boring node → cheap model
      }))
    );

    // REDUCE — plain code, no model, no tokens
    const findings = dedupeBySource(raw.flat().filter(Boolean));

    // VERIFY — a FRESH skeptic per finding, tries to kill it
    const survivors = await parallel(
      findings.map(f => () => agent({
        task: "try to disprove this. return keep | drop + why.",
        input: f,
        freshContext: true,     // never reuse the researcher's chat
        model: "strong",        // judgment node → strong model
      }))
    ).then(v => findings.filter((_, i) => v[i].verdict === "keep"));

    // SYNTHESIZE — one agent writes the answer from what survived
    return agent({ task: "one report, ranked by confidence, sources attached.",
                   input: survivors, model: "strong" });
    ```
  - The whole craft in one read
    - Fan-out where work is independent
    - Reduce in free code
    - Verify on a **fresh context**
    - **Cheap models on boring nodes, strong model where judgment lives**
    - One synthesize at the end
  - Same skeleton for a market scan, code review or research report — swap the angles and prompts
- **6 · The checker is the whole trick**
  - Every serious test of AI self-review: **models miss most of their own mistakes**
  - **Never let the agent that did the work check the work**
    - Put a separate node on the edge whose only job is to **try to kill the finding**; survives → passes, else dies there
  - **The checker needs a clean context**
    - Same chat as the worker → it's just nodding along "in a different font"
    - A graph of agents sharing one context is **a single loop in a costume** — breaks the same way, later and pricier
  - Check a **real signal**: not "did the agent say it's done" but "does the test actually pass"
  - **Split checking three ways**: is it correct? is it current? is the source real? — three lenses catch what ten identical ones miss
    ```text
    ▸ VERIFIER NODE
    INPUT:    one finding from a worker (the finding only, never the worker's chat)
    CONTEXT:  fresh and empty. it has not seen the work it is judging
    CHECKS:   three skeptics run in parallel, each with a different question
      1. is it correct?      → does the claim actually hold up
      2. is it current?      → is the source recent, not something stale
      3. is the source real? → does the link resolve to the claim it's cited for
    PASS:     keep the finding only if a majority of skeptics let it live
    FAIL:     drop it before it ever reaches the final answer
    ```
  - **Rule: a worker and its verifier must never share a context** — otherwise it's one loop grading its own homework with a bigger bill
- **7 · Where graphs actually break**
  - **1. Context collapse**
    - Fan out 1,000 nodes, feed all outputs into one step → blow the context window before synthesis starts
    - Fix: **layer the fan-in** — batch, summarize each batch, combine the summaries, never the raw pile
    ```javascript
    // layered fan-in — never pour 1,000 raw outputs into one step
    const batches = chunk(results, 40);              // groups of 40
    const summaries = await parallel(
      batches.map(b => () => agent({ task: "summarize this batch", input: b }))
    );
    return agent({ task: "write the answer from the summaries", input: summaries });
    // the final step reads ~25 summaries, not 1,000 raw outputs
    ```
  - **2. False independence**
    - Two nodes look independent but write to the same file or hit the same rate-limited API → **a hidden edge**
    - When Bun's team first fanned a big job across many agents, they shared one workspace and overwrote each other
    - Fix: give every worker **its own isolated space**; audit for **shared resources**, not just shared data
    ```javascript
    // isolate the workers — no shared file, no shared workspace
    await parallel(files.map(f => () => agent({
      task: `refactor ${f}`,
      worktree: true,        // each agent works in its own git worktree
    })));
    // they can't overwrite each other, then the results merge cleanly
    // rule: any two nodes writing the same file need an edge, not parallelism
    ```
  - **3. Silent node failure**
    - In a chain, one failure stops everything (obvious); in a graph, one dead node among 200 can slip into a report that **looks complete**
    - Fix: every merge step **counts inputs vs expected** and flags the gap
    ```javascript
    // fan-in guard — catch the node that quietly died
    const results = (await parallel(jobs)).filter(Boolean);   // dropped nodes = null
    if (results.length < jobs.length) {
      flag(`WARNING: ${jobs.length - results.length} of ${jobs.length} nodes returned nothing`);
    }
    // never synthesize on a partial set and call the report complete
    ```
- **8 · Do you even need one?**
  - **A graph buys breadth. It does not buy better judgment.** When the work isn't wide, the line was never the problem
  - **Skip the graph when**
    - The task is small or isolated (one function, one bug) — coordination is pure overhead
    - You want to approve every step — a graph's point is running wide without you
    - You don't yet know what you're looking for — exploration wants one steerable agent
    - Steps genuinely depend on each other — forcing a graph adds cost for zero speedup
    - **The tell**: if the fake-edge test can't find two jobs with no edge between them, there's no graph — it's a loop, and a loop is fine
- **9 · The part nobody wants to hear: anchors**
  - Imagine the full graph: paired checkers, audit nodes, meta-nodes tuning other nodes — every node reads a report
    - The audit checks numbers against finance numbers that came from the same system
    - **Everything is consistent. Nothing is verified.**
    - Fails like the single loop — later, more expensively, with more green lights on the way down
  - **Topology alone does not buy truth. The graph needs anchors**: nodes that cannot be argued with
    - Tests that actually ran and passed (not "should pass")
    - Revenue that landed in the bank
    - Customers who actually stayed
  - Some **rules must be frozen** — the ones an optimizer would be tempted to weaken to win
  - **The graph is only as honest as the things inside it that refuse to move**
    - Judge on numbers that can't argue back → grounded; let it grade its own reports → confidently wrong

- **12 · The cost and the supervision**
  - A graph costs **much more** than a normal chat — coordination gets cheaper, not the work; a fleet burns a pile of tokens
  - **Public example: rewriting the Bun runtime**
    - ~**535,000 lines** translated into **over a million lines** of another language in ~**11 days** (≈ a year by hand)
    - ~**50 workflows**, up to **64 agents** at once
    - Cost ~**$165,000** in usage, needed a human designing and watching it, and drew criticism over whether that much AI-written code can be reviewed safely
  - A graph can fan out to 1,000 agents — and can **quietly spend your money** if pointed at the wrong task or run without anchors
  - The heavy version is for teams with **budget, caps and monitoring**; otherwise start small, watch what a run costs, widen only once one has earned it
- **13 · What this means for you**
  - Strength: **breadth** — independent work done at once
  - Weakness: buys **width, not judgment**, and spends money on the wrong job
  - The move is not to graph everything — it's knowing **when the work is wide enough**, and when a simple loop was the answer
  - **Author's take: learn the fake-edge test tonight** — draw your workflow, find edges that carry no data, delete them
  - Most will keep queueing steps in a line; the few who learn to draw the graph will run a fleet
